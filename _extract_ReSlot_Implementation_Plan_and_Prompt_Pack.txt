1. Purpose and how to use this pack
This is the build plan for ReSlot, the timetable rescheduling platform for the Department of Computer Engineering,
JSPM's Rajarshi Shahu College of Engineering (RSCOE), Pune. The frontend is prototyped in Lovable with mock
data and then connected to a real backend built in Antigravity. The plan covers architecture, design system,
screens, API, phases, migration from mock to real data, testing, security, deployment, and every prompt needed to
build the project from zero.

Part 1 (this plan): what to build, in what order, with what acceptance criteria.

Part 2 (prompt pack): 70 ready-to-paste prompts in five series: L (Lovable), A (Antigravity), M (mock-to-real
integration), Q (quality and release), G (generic templates). The same prompts are in ReSlot_Prompt_Pack.md
for easy copy and paste.

Inputs you already have: schema.sql, seed.sql, master_timetable.txt, build_seed.py, input_example.json and
the final draft PDF. Several prompts say 'attach' these files.
Ground rules for running the prompts

One prompt at a time, in the order of the phase table. Wait for it to finish, review the result, run its 'Done when'
check, commit, then continue.

Lovable: use Plan mode first for every large prompt, read the plan, then switch to Build. Plan messages cost
credits, so keep prompts focused and avoid re-running whole prompts for small tweaks (use the G-01 template
instead).

Antigravity: use Planning mode for anything touching more than one file. Review the implementation-plan
artifact and comment on it before approving. Keep tasks small and let the rules in AGENTS.md do the repeating.

Replace every <placeholder> and attach the files a prompt names. Never paste secrets (API keys, tokens) into
either tool; use environment variables.

If a result drifts from the domain rules (master is read-only, only hit sessions change, nothing publishes without
validation), stop and correct it with prompt G-03 before building on it.

Repositories and branching

Two repositories. Lovable expects the app at the repository root, so keep the backend out of the Lovable
repository. reslot-web is synced with Lovable; reslot-api is edited in Antigravity.

Contract hand-off. The backend publishes docs/openapi.yaml (prompt M-01). The frontend copies it into
reslot-web (docs/openapi.yaml) and generates types from it (prompt M-02).

Environments. The frontend reads VITE_API_BASE_URL and VITE_USE_MOCKS; the backend reads
CORS_ALLOWED_ORIGINS. Local stack: docker compose for the API and PostgreSQL; the frontend runs in
Lovable preview or locally with npm run dev.
Lovable working rules (from current Lovable documentation; confirm in your workspace)

Connect GitHub early: two-way sync works on the default branch (main). Other branches do not sync until
merged. Every agent change becomes a commit.

Never rename, move or delete the connected repository: it permanently breaks sync.

Do not edit the same project in Lovable and in an external editor at the same time; pull before you push; wait for
Lovable changes to reach GitHub before external edits.

Use Knowledge for rules that must apply to every request, Plan mode before large changes, version history to
undo, and attach screenshots or logos when you need a visual reference.

Do not enable Lovable Cloud or Supabase for this project; the backend is the Spring Boot API (this is stated in
the Knowledge prompt).
Antigravity working rules (from current guides; confirm in your version)

Agent-first IDE with an Agent Manager (orchestrate agents) and an Editor view. Planning mode produces plans
and artifacts (task list, implementation plan, walkthrough) you can comment on; Fast mode skips planning for
small changes.

Rules: AGENTS.md at the repo root is read in recent versions; rules also live in .agents/rules (older versions:
.agent/rules); each rules or workflow file is capped at 12,000 characters. Workflows are saved prompts triggered
with a slash command. Global rules live in ~/.gemini/GEMINI.md.

Safety: use Secure mode or a command deny list when agents run terminal commands; keep secrets out of the
workspace; review every migration before it runs against a shared database.

Run several agents in parallel only on separate packages (for example solver and notifications) to avoid
conflicting edits.
The mock-to-real strategy in one picture

1. Prototype everything in Lovable against src/api adapters that read mock fixtures (VITE_USE_MOCKS=true).
Components never call fetch.

2. Build the backend in Antigravity module by module; every endpoint is documented in OpenAPI.

Brand source: the college website's stylesheet could not be read while preparing this plan, so the palette is inspired by the red,
maroon and black of the JSPM and RSCOE logos (visible on the college timetable header) and by conventional institutional
design. Contrast ratios are approximate. Run prompt L-02 with screenshots of the website and the logos to confirm or adjust the
exact values before building further screens.
Typography, layout and components

Type: Inter for the interface (400, 500, 600) and Source Serif 4 for page titles; scale 12, 14, 16, 20, 24, 32 px;
tabular numerals for times.

Shape: 8 px radius (cards 12 px), 1 px borders, very light shadows, no gradients. Generous whitespace; 4 px
spacing grid.

Shell: deep maroon top bar with the JSPM and RSCOE logos and the text 'Department of Computer Engineering
- ReSlot'; collapsible sidebar grouped as Overview, Master, Operations, Communication, Insights, Administration;
global Working date pill; command palette (Ctrl/Cmd+K); AI assistant panel (Ctrl/Cmd+J).

Core components: PageHeader, KpiCard, StatusBadge, DataTable, EmptyState, ErrorState, SkeletonTable,
ConfirmDialog (typed confirmation), Stepper, Drawer, Legend, TimetableGrid, BlastRadiusList, PlanCard,
ClashChip.

Status vocabulary: Unchanged (neutral), Rescheduled (warning), Room changed (info), Cancelled (danger,
struck through), Pre-existing clash (amber hatched outline), New clash (danger solid), Pending, Approved,
Published, Failed.

Timetable grid: Mon-Sat columns; P1-P7 rows with thin recess and lunch separators; 2-hour labs as merged
cells; parallel batches as stacked sub-cards; joint-class tag; lock icon on fixed sessions; review dot on flagged
sessions; below 768 px a day list replaces the grid.

Accessibility: WCAG 2.2 AA, visible 2 px focus ring, skip link, keyboard-operable grid and drawers, status never
conveyed by colour alone (icon plus text), reduced-motion support, 44 px touch targets on the portal.

Motion: 150-200 ms fades and slides only; no decorative animation on data views.

Content tone: plain, institutional, no jargon, no emojis; dates like '22 Oct 2026 (Thu)'; 24-hour times.

Phase details

Phase 0 - Foundations. Create reslot-web and reslot-api repositories; create the Lovable project, paste
Knowledge (L-00), connect GitHub; open the backend in Antigravity and run A-00. Create accounts: Meta
developer and business account (WhatsApp), an LLM API key, an SMTP sender, a cloud project. Decide hosting.
Deliverable: both tools produce a hello-world; a small commit round-trips through GitHub.

L-00 Project Knowledge (paste once)
Tool: Lovable | Phase 0 | Mode: Paste into Knowledge (Chat actions > Knowledge)
 PRODUCT
ReSlot is the timetable rescheduling platform for the Department of Computer Engineering, JSPM's Rajarshi Shahu College of
Engineering (RSCOE), Pune. Staff upload the department's master timetable, enter what changed for a date (rooms/labs/faculty
unavailable, extra rooms/labs, room rules), and the system proposes a conflict-free updated timetable for that date, gets it
approved, publishes it and sends personalised WhatsApp messages to affected faculty and students.
ROLES
COORDINATOR (timetable coordinator): uploads and verifies the master, enters disruptions, runs the solver.
HOD: approves/rejects and publishes plans, sees the audit log.
FACULTY: sees own timetable and changes, manages notification preferences.
STUDENT (class representative): sees division/batch timetable.
ADMIN: users, settings, integrations.
DOMAIN LANGUAGE (use these exact terms in the UI)
Master timetable (read-only once active), Version, Session, Division (SY-A...), Batch (SA1...), Elective cohort, Joint class, Lab
block (2 hours), Classroom, Lab, Disruption, Room rule, Plan, Blast radius, Override, Pre-existing clash (already in the master,
never hidden) vs New clash (introduced by a plan, blocks approval), Publish, Notification.
RULES
- The master timetable is the source of truth. Never edit it in the UI; corrections create a new version.
- Only sessions hit by a disruption may change; show everything else unchanged.
- Labs run in fixed 2-hour blocks (09:00-11:00, 11:15-13:15, 14:00-16:00). Classrooms are booked by 1-hour period.
- Periods: P1 09:00-10:00, P2 10:00-11:00, short recess 11:00-11:15, P3 11:15-12:15, P4 12:15-13:15, lunch 13:15-14:00, P5
14:00-15:00, P6 15:00-16:00, P7 16:00-17:00. Days Mon-Sat. Timezone Asia/Kolkata.
- Unknown data stays unknown: show 'Not specified' with a review flag; never invent values.
TECH
React + TypeScript + Vite + Tailwind + shadcn/ui, React Router, TanStack Query, React Hook Form + Zod, date-fns, Recharts,
lucide-react. Do NOT use Supabase or Lovable Cloud: the backend is a separate Spring Boot REST API. All data access goes
through src/api (typed adapters); VITE_USE_MOCKS=true uses fixtures in src/mocks. Never call fetch from components.
Structure: src/features/<module>/{components,hooks,pages}, src/components/ui (shadcn), src/lib, src/api, src/mocks, src/types.
Keep components under 300 lines; split when larger.
DESIGN
Institutional, calm, data-dense but airy. RSCOE-inspired crimson/maroon on warm white; tokens live in src/index.css and
tailwind.config.ts. WCAG 2.2 AA, visible focus rings, keyboard navigable, responsive from 360 px. Every screen has loading
skeletons, empty and error states. Dates like '22 Oct 2026 (Thu)'; times in 24-hour format. No emojis in UI text; use lucide-react
icons.
Done when: Knowledge saved; later prompts do not need to repeat product context.

# ReSlot API - agent instructions
Spring Boot backend for ReSlot, the timetable rescheduling platform of the Department of Computer Engineering, RSCOE
Pune.
## Non-negotiable domain rules
1. The master timetable is the source of truth and is read-only once its version is ACTIVE (enforced by DB triggers). Never write
code that updates master sessions. A correction is a new version.
2. Disruptions record what happened; schedule_overrides record the response. Always store the original room and time on an
override.
3. Only sessions hit by a disruption may change. Everything else stays exactly as in the master.
4. The master may contain its own clashes. They are the accepted baseline (pre_existing = true): never edit or hide them. Only
clashes introduced by a plan block approval.
5. Nothing is published or sent unless (a) the independent validator reports zero NEW clashes and (b) a human approved.
6. Labs run in fixed 2-hour blocks; classrooms are booked by 1-hour period; intervals are [start, end).
7. Unknown stays unknown: NULL plus needs_review, never guessed.
8. LLM output is never trusted. It may only produce a structured proposal that a human confirms. No LLM call may write
timetable data.
## Stack
Java 21+ (LTS), Spring Boot (latest stable), Spring Web, Validation, Security (JWT), Data JPA plus JdbcTemplate for SQL
functions, Flyway, PostgreSQL 16, OR-Tools CP-SAT (Java), springdoc-openapi, Micrometer, Testcontainers, JUnit 5.
Package by feature under com.rscoe.reslot: identity, masterdata, ingestion, timetable, availability, scheduling, approval,
notification, assistant, audit, reporting, shared.
## Conventions
- Controllers are thin, services hold logic, repositories only access data. DTOs are records; never expose entities.
- Every endpoint is documented with OpenAPI annotations; errors are RFC 9457 problem+json with stable error codes.
- Times: LocalTime/LocalDate, one Clock bean, business zone Asia/Kolkata.
- Database changes only through Flyway migrations V<number>__<name>.sql; never edit an applied migration.
- Idempotency: POSTs that create runs, overrides or notifications accept an Idempotency-Key header.
- Transactions at service level; publish plus outbox rows happen in ONE transaction.
- Logging: structured JSON with correlation id; never log phone numbers or tokens.
- Secrets only from the environment; never commit .env.
## Testing
Every feature ships with unit tests and Testcontainers integration tests. Golden tests: the seeded master has exactly 22 room
clashes, 19 faculty clashes and 0 group clashes. Solver plans must always pass the independent validator (property tests).
## Workflow
Work in small tasks. Plan first for multi-file changes. Run ./mvnw verify before finishing. Update docs or an ADR when a decision
changes. Never run destructive commands (drop database, force push, rm -rf outside build directories).
Done when: Ask the agent 'which domain rules apply when a plan is published?' and it answers from AGENTS.md.
